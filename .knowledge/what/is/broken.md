The structured frontend and elastic RTL work remain incomplete. Passing focused tests do not establish full compiler acceptance.

- **Co-slice gives the last destination the whole aggregate.** For a multi-destination co-sliced transfer the prototype assigns the full packed aggregate to the last destination instead of its slice. In `tests/coslice.pigen` (four 8-bit destinations) the emitted `state_delay <= ({source + 8'd1, source + 8'd2, source, state});` assigns 32 bits to an 8-bit register; `tests/transfer_block.pigen` emits the same pattern (24 bits into 8). Verilog's implicit truncation keeps the low bits, which here happen to be the correct slice, so `coslice-test` and the other simulations pass. Verilator reports both as `WIDTHTRUNC` warnings, which `make verify` does not treat as failures (its lint runs with `-Wno-fatal`). This violates the packed bit-stream order contract and would produce wrong values whenever the last destination is not the lowest slice.
- **Task 6 declaration lowering is incomplete on master.** The BOUNDARY realization is implemented: pigen_lower_rtl_module_declarations dispatches by the source descriptor's realization through a private realization-indexed adapter table (no source transfer-type enum value appears in src/rtl_lower.c) and publishes the three-port input shape for BOUNDARY (a VARIABLE payload object carrying the lowered data type and semantic direction, plus context-dependent valid/ready control expression records, the input side exposing the same three objects). The net/variable payload realizations are implemented: COMBINATIONAL_NET and PROCEDURAL_VARIABLE each publish exactly one VARIABLE payload object (the lowered data type memo's type record, the semantic direction, the input side the same object) with no storage instance; their valid/ready constant controls are not published on master yet, so the endpoints record's valid/ready expression identities stay invalid until those controls land. The four storage realizations are implemented: ELASTIC_SLOT / PULSE_REGISTER / PARAMETERIZED_QUEUE / SKID_QUEUE each publish exactly one VARIABLE payload object (the lowered data type via the type memo, the semantic direction, the input side the same object) plus exactly one pigen_rtl_instance owned by the semantic module, the parameterized queue carrying its semantic depth (lowered from the transfer argument const-expr through the expression memo) as the instance's single ordered parameter so the value round-trips exactly, and valid/ready driven by the primitive so no constant control expression is published. On master, sections 1-8 and 12-15 of tests/rtl_lower_test.c are green, and sections 9-11 report their first deliberate unimplemented-behavior reds: section 9 (t6-net-variable-payload) at tests/rtl_lower_test.c:1862 (the four valid/ready control identities must each resolve through pigen_rtl_expr_get to a PIGEN_RTL_EXPR_INTEGER record with a 1-bit literal; without published controls they are PIGEN_INVALID_ID and resolve to NULL), section 10 (t6-net-variable-controls) at tests/rtl_lower_test.c:2069, and section 11 (t6-net-variable-counts) at tests/rtl_lower_test.c:2327 — the only red sections. The verified constant-controls implementation exists on branch work/elastic-rtl-task-6-impl-net-variable-constants (commit 875ac7f) and passes every section against the corrected section 9 witness: it publishes the descriptor 1-bit valid/ready constants as expression records, so the section 9 control-record witness, the section 10 constant asserts and the section 11 count deltas all hold there (WIRE valid 1 / ready 0, REG valid 1 / ready 1, the two valid constants internable to one shared 1-bit record). After the constant-controls landing, the whole-unit ready graph, atomic fire, ordered output, SV emission, quarantined composition and complete verification remain open. See the task owners and plan.
- **Plain pigen_rtl_module_add leaves the new record partly uninitialized.** src/rtl.c's pigen_rtl_module_add sets only record->origin; semantic_module and the objects/instances/equations/processes owner ranges stay uninitialized, unlike pigen_rtl_module_add_with_owner which initializes every field. Any owner-tagged add (e.g. pigen_rtl_object_add_with_owner) under such a module reads the uninitialized owner range, so acceptance is nondeterministic. No production caller exists today (only tests/rtl_test.c uses the plain form); the remaining Task 6 declaration realizations must add RTL modules through the with-owner constructor (or the plain form must be fixed) to publish payload objects under a freshly added module.
