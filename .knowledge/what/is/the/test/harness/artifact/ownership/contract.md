A test harness must build and execute each artifact inside a fresh, invocation-owned directory and clean it up, so a run observes only the binary it just compiled. Fixed shared output paths are a defect: if another build or an external editor writes the same path between the compile and execute steps, the harness executes a different binary than the one it compiled, and a source that genuinely fails its test reports pass.

The production `Makefile` C compile/execute targets — the fifteen `pigen-*-test` targets from `source-test` through `sv-emit-test` — built to and executed a fixed shared path `/tmp/pigen-<name>`. Every target's compiler options, `$(T)` section selection and exit status are correct; only the output location is the defect. The SV/pipeline/waveform targets write `.sv`/`.vvp`/`.verilator` products to `/tmp` for separate simulator runs and are outside this concern.

Requirement per target: first remove the target's own legacy fixed path `/tmp/pigen-<name>` (it owns that path and must not leave an occupant there — what the ownership witness checks), then create a fresh directory (mktemp -d), compile the unchanged source list and CFLAGS into `$dir/<name>` (a compile failure must still propagate nonzero), run `$dir/<name>` preserving any section-selection argument, exit with the run's status, then remove the directory. Only the output location and its invocation change; every source list, compiler option, section selection and exit status is preserved.

The hidden pin `tests/harness_artifact_ownership.sh` (one `contracts.json` entry, `sh tests/harness_artifact_ownership.sh`) witnesses the property on `source-test`, the canonical representative of the fifteen. Its accepted form is INCOMPLETE: its marker is non-runnable (mode 644), so nothing observes that the run executed in a fresh invocation-owned directory — only that the fixed path was absent after and that `make` returned 0. A recipe that compiles to the fixed path (overwriting the marker), executes it, and then `rm -f`s it leaves the path absent and returns 0: both properties pass (green) while the run still compiled and executed at the shared path, the exact defect the property forbids. The pin is therefore being strengthened to witness invocation-owned execution (a runnable sentinel the run must not fire) so that escape fails and only the fresh-`mktemp -d` form passes.

`tests/**` and `Makefile` are protected harnesses; an implementation worker must not edit them, and the CointOS landing gate refuses an implementation-stage commit that changes them. The repair therefore routes through the ordinary test-contract lane, the stage that owns both `tests/**` and the `Makefile`.

Current state: UNMET on `master` — all fifteen targets still build to and run the fixed `/tmp/pigen-<name>` path (no `mktemp -d`), so the defect is live. The corrected form (the single added line `rm -f /tmp/pigen-<name>` per target) is verified green on a retained branch (commit 85be45a on `work/harness-artifact-ownership-impl`) but not yet on master; it is routed through the test-contract lane (a packet carrying the `Makefile` repair, dependent on the strengthened pin) because the implementation lane's protected-harness gate refuses it.
