A test harness must build and execute each artifact inside a fresh, invocation-owned directory and clean it up, so a run observes only the binary it just compiled. Fixed shared output paths are a defect: if another build or an external editor writes the same path between the compile and execute steps, the harness executes a different binary than the one it compiled, and a source that genuinely fails its test reports pass.

The production `Makefile`'s fifteen C compile/execute targets — `pigen-*-test` from `source-test` through `sv-emit-test` — historically built to and executed a fixed shared path `/tmp/pigen-<name>`. Every target's compiler options, `$(T)` section selection and exit status are correct; only the output location is the defect. The SV/pipeline/waveform targets write `.sv`/`.vvp`/`.verilator` products to `/tmp` for separate simulator runs and are outside this concern.

Requirement per target: first remove the target's own legacy fixed path `/tmp/pigen-<name>` (it owns that path and must not leave an occupant there — what the ownership witness checks), then create a fresh directory (mktemp -d), compile the unchanged source list and CFLAGS into `$dir/<name>` (a compile failure must still propagate nonzero), run `$dir/<name>` preserving any section-selection argument, exit with the run's status, then remove the directory. Only the output location and its invocation change.

The red pin `tests/harness_artifact_ownership.sh` (one `contracts.json` entry, `sh tests/harness_artifact_ownership.sh`) witnesses the property on `source-test`, the canonical representative of the fifteen. Property 1 (no fixed path) plants a marker at `/tmp/pigen-source-test`, runs `make source-test`, requires the path absent afterward; a mktemp-only recipe leaves the marker in place and fails it. Property 2 (no false pass / owned execution) requires the run to report the compiled test's own status, not the marker's. The fix is the minimal superset of the mktemp form: one added line `rm -f /tmp/pigen-<name>` per target.

Current state: UNMET on `master`. All fifteen targets still build to and run the fixed `/tmp/pigen-<name>` path (`source-test` compiles to and runs `/tmp/pigen-source-test` with no `mktemp -d`), so the red pin is red. The pin as accepted is also INCOMPLETE: its marker is non-runnable (mode 644), so nothing observes that the run executed in a fresh invocation-owned directory — only that the fixed path was absent after and that `make` returned 0. A recipe that compiles to the fixed path (overwriting the marker), executes it, and then `rm -f`s it leaves the path absent and returns 0: both properties pass (green) while the run still compiled and executed at the shared path, the exact defect the property forbids. The property is therefore under-enforced; the pin must be strengthened to witness invocation-owned execution (show the run executed in a fresh owned directory, not merely that no fixed-path occupant remains) and to reject that build-to-fixed-path-then-delete escape for each of the fifteen targets.

`tests/**` and `Makefile` are protected harnesses; an implementation worker must not edit them directly. The fix therefore routes through the ordinary test-contract path, not a direct worker edit.
