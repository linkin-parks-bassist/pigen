Yes. Ordinary SV child instantiation is specified and the structured syntax level parses it on master. The child-instance grammar: one module-level item is an instance when an identifier that is not a decisive Pigen count type or structured typedef is followed by an instance-name identifier (or `#( ... )`) and a `(`, and it parses to a PIGEN_SYNTAX_INSTANCE with the type-name and instance-name tokens plus half-open child ranges over its PIGEN_SYNTAX_PARAMETER (is_local 0) and PIGEN_SYNTAX_INSTANCE_CONNECTION children in source order, the whole-item span ending at the terminating `;`. A missing `;`, an unterminated parameter or connection list, a malformed connection, or a connection that is neither `.port ( expression )` nor an expression fails loudly at the offending token's original span, with no fallback to declaration or opaque; a decisive data-first declaration of the same identifier-identifier-`(` shape takes the declaration route (fail-loud at the `(`) and never publishes an instance node. The type name is a stored token; module-name and port resolution are not part of this step. This contract is pinned green by the registered instance-syntax-test manifest (tests/instance_syntax_test.c: parameter-mixed-connections, empty-params-named-only, fail-loud-reds, data-first-not-instance) and two syntax-model assertions (ordinary `buf gate_instance(a, b);` parses to an instance with two connections and zero parameters; the unterminated form fails with `instance requires `;`` at the endmodule span). Fabric semantics must depend only on resolved instance/port identities so future spelling cannot alter routing or force fabric-specific name parsing.
