analyze_handshake_call in src/expression_analysis.c builds typed CALL records for peek, valid, ready and accepts without publishing semantic expressions, lvalues, children or width constraints. expression_analysis.h stores the semantic call kind, analyzed first/second operands and validated signal identity in as.call. This is an intrinsic analyzed record, not a new parsed expression kind.

peek preserves its argument's data type, shape and eligible cached constant. Its argument uses the local sizing/fill boundary owned by how/are/expression/call/arguments/sized.md. Cached peek constants convert at that boundary instead of propagating enclosing context into the argument. Nonconstant peek operands retain invalid constant recipes. valid/ready/accepts return pigen_data_type_boolean and never acquire fabricated runtime constants.

valid/ready require an analyzed direct signal reference; native channel expressions resolve to their canonical signal identities. accepts requires a structural signal/projection/concatenation lvalue destination and a direct signal source. analyzed_lvalue validates groups, signal-based packed/unpacked projections and concatenations without constructing lvalues. A projection over a concatenation is not a signal-based projection. Unknown names, unsupported computed control sources and malformed arities reject. The direct accepts resolver checks the semantic source kind before reading its symbol union member.

Materialization in src/expression_resolve.c uses the existing pigen_expr_add_peek/control/accepts constructors; accepts constructs its destination lvalue then. Control records carry signal identities rather than consuming payload reads. Query operands are type-inspected and discarded, so `$bits(peek(bus.aw).addr)` and widths of valid/ready/accepts expressions create no handshake dependencies. Runtime array dimension arguments materialize the calls and preserve their existing observational semantics. Constant-only coordinates still reject runtime controls.
