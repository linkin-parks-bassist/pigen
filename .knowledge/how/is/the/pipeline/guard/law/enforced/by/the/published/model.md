The guard law (include/pigen/pipeline_lower.h step (c), how/to/reset/and/enable/a/pipeline.md) is unambiguous and normative: when the enclosing procedural guard is false the pipeline holds every stage's storage AND disables both the input and the output handshake, so no item is accepted or emitted that cycle; "the pipeline's ready/valid equations are ALL gated by that guard." A phase-local stand-in that gates only the ready equation's value is not an acceptable narrowing: the law says all equations are gated, and a false guard must hold storage and disable both handshakes in effect, not merely in the ready equation's expression value.

The gap found in the landed step-(c) implementation (src/pipeline_lower.c, commit d33e788): the guard is applied to exactly one published equation, `ready = guard`, whose destination is a dangling internal 1-bit object (PIGEN_SEMANTIC_INTERNAL, invalid signal, invalid span) that is not a module port and is not wired into the transfer handshake model. The per-stage next-value equations are constant-0 stand-ins with the guard explicitly unused, the buf stage storage instance publishes no guard/valid port, and the final yield to the outgoing-packet write is unconditional. So in the published model a false guard neither holds any stage's storage, nor disables either handshake, nor stops the yield from emitting. The six halting/stop test sections over the pipeline-lower-test seam check only the ready equation's value (constant-1 stand-in vs. carrying the guard's spelling), so a lowering that publishes a standalone `ready = guard` on a dangling object, leaves the stage storage and the yield write ungated, and never wires the guard to any input/output port or to storage passes all six and leaves the storage-hold and I/O-handshake obligations unenforced.

The RTL model can express the hold: `pigen_rtl_expr_add_conditional` is a mux (`condition ? when_true : when_false`), so a false guard holding a stage's storage is a conditional over the guard, the computed next value, and the stored value; the input and output handshake controls are the same ready/valid equations ANDed with the guard. The storage-hold wiring therefore composes on the per-stage next-value contract (plan item 1, the stand-in replacement): the hold's when-true branch is the computed next value that item publishes, and its when-false branch is the stored value, so the wiring depends on the stand-in replacement rather than racing it.

Disposition: the next owner wires the guard into the published model's storage update and input/output handshake, not a narrow the law. The six accepted ready-equation sections stay as-is; the storage-hold and I/O-handshake obligations are added as their own scoped test contract and implementation, depending on the accepted stand-in-replacement packet (plan item 1).
